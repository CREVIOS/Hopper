Requirements that refer to ``VM'' or ``hypervisor'' are interpreted as \textbf{session workloads} and the \textbf{Kubernetes API}, unless explicitly marked as a future adapter.

\section{Problem Definition}

\subsection{Problem Statement}

\subsubhead{What Problem Are We Solving?}

Students doing machine learning or deep learning projects often run into the same frustrating situation - they need a serious GPU to train models or run experiments, but the only options available are either expensive cloud services (AWS, Google Cloud, Modal) or waiting in long queues for shared university HPC clusters. A lot of the time, students end up having to pay out of pocket for cloud GPU hours, or they just give up and run things on their laptops, which is obviously terrible for anything non-trivial.

At the same time, many universities and research labs actually have powerful hardware sitting around - high-end NVIDIA GPUs like the RTX PRO 6000 Blackwell, RTX 5090, 3090, and 4070. The problem is that these GPUs are not easily accessible to students in a self-service way. There is usually some admin overhead involved, no real billing or quota system, no isolation between users, and no clean way to provision and deprovision environments on-demand.

Hopper Cloud is trying to fix exactly this. The idea is to take bare-metal GPU hardware that a university or lab already owns, wrap it in a proper Kubernetes-based orchestration layer with container-level isolation (using gVisor syscall interception), and expose it to students through a clean web portal - similar to how Modal or Lambda Labs works, but running locally and managed by the institution. Students get their own isolated GPU environment, a credit-based billing system so usage is fair and trackable, and SSH access through a secure Teleport gateway.

\subsubhead{Why Does It Matter?}

The gap between what students need and what is available to them right now is pretty significant. Running even a modest fine-tuning job on a small transformer model needs at minimum 8--16 GB of VRAM, which rules out most consumer hardware. Cloud costs are also genuinely prohibitive - an A100 on AWS can run \$3--4/hour, which adds up fast for a student working on a semester project.

Beyond the cost issue, there is also a security and fairness angle. When shared GPU machines are accessed without proper isolation, one student's badly-written training loop can crash the system for everyone. Without a billing/quota system, there is no accountability - a few power users can hog all the resources. And without proper audit logging, there is no visibility into how resources are being used.

Hopper Cloud solves all of these at once: it democratizes access to powerful compute, enforces fair usage through credits, isolates workloads at the container level using gVisor so one user cannot affect others, and gives administrators full visibility into usage through audit logs.

\subsection{Goals and Non-Goals}

\subsubsection*{Goals}

\begin{itemize}[leftmargin=1.5em]
  \item Provide students with self-service, on-demand access to heterogeneous GPU resources through a simple web portal.
  \item Implement a credit-based billing system where usage is tracked transparently and sessions auto-terminate when credits are exhausted.
  \item Ensure strong workload isolation using gVisor container runtime (syscall interception in userspace) - one student's session cannot interfere with another's.
  \item Enforce zero-trust network security using Calico GlobalNetworkPolicy, with all inter-pod traffic default-denied.
  \item Provide secure SSH access to provisioned pods through the Teleport bastion host with ephemeral keys.
  % \item Enable GPU partitioning using NVIDIA MIG for the RTX PRO 6000 Blackwell (up to 4x24GB slices) and time-slicing for consumer GPUs (5090/3090/4070).
  \item Automate session lifecycle management - provisioning, credit metering, expiration, and cleanup - through the Reaper service.
  \item Maintain a full audit log of all sessions, credit transactions, and authentication events in PostgreSQL.
  \item Give administrators visibility into cluster health, GPU utilization, and per-user usage through a management interface.
  \item \textbf{(VMpire)} Provide optional \textbf{approval workflows} so lab administrators may approve or reject provisioning requests before resources are created, when institutional policy requires it.
  \item \textbf{(VMpire)} Support \textbf{quota policies} scoped per user, course, or department (beyond credit-based metering alone).
  \item \textbf{(VMpire)} Provide \textbf{real-time vitals} (CPU, memory, disk, network where available) and \textbf{expiration awareness} for all student workloads visible in the portal.
\end{itemize}

\subsubsection*{Non-Goals}

\begin{itemize}[leftmargin=1.5em]
  \item Hopper Cloud is \textbf{not} a general-purpose cloud platform - it is scoped to GPU compute and does not offer managed databases, object storage, or serverless functions.
  \item The system will \textbf{not} provide a custom IDE or JupyterHub in v1; students are expected to SSH in and manage their own development environments.
  \item Hopper Cloud is \textbf{not} multi-tenant in the commercial SaaS sense - it is designed to run within a single institutional network, not as a public-facing service.
  \item We are \textbf{not} building a payment/money gateway - credits are institutional allocations, not purchased with real money in v1.
  \item Automated hardware provisioning (adding new physical GPU nodes to the cluster) is \textbf{out of scope} - the physical cluster is assumed to be pre-configured by platform engineers.
  \item Custom container image building or Docker registry management is \textbf{not} included in scope for this version.
\end{itemize}

\begin{notebox}[Withdrawn non-goal from prior standalone VMpire SRS]
The standalone VMpire SRS stated that supporting Kubernetes/container workloads was out of scope. For the \textbf{combined Hopper} project, \textbf{Kubernetes is the implementation platform}; that prior non-goal is \textbf{withdrawn}.
\end{notebox}

\section{Scope and Context}

\subsection{In Scope}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{User Portal (SvelteKit 2 / Svelte 5):} Web-based dashboard for students to view credit balance, browse available GPU configurations, request sessions, monitor active sessions, and view session history.
  \item \textbf{Authentication System:} OIDC/SAML-based login via Keycloak, supporting institutional SSO through university Shibboleth identity providers with attribute mapping.
  \item \textbf{Session Orchestrator:} Go service using client-go (the native Kubernetes SDK) and gRPC to provision student pods, manage pod lifecycle state machine, and coordinate with the billing system.
  \item \textbf{Credit and Billing Engine:} Double-entry bookkeeping credit ledger with append-only immutable entries, advisory locks for race condition prevention, and per-minute metering with full transaction history.
  \item \textbf{GPU Provisioning:} Dynamic pod scheduling to appropriate GPU nodes using NVIDIA GPU Operator resource profiles; MIG slicing for RTX PRO 6000 Blackwell; time-slicing for RTX 5090, 3090, 4070.
  \item \textbf{Container Runtime Isolation:} gVisor (runsc) runtime class for all student pods, intercepting syscalls in userspace for security isolation without VM boot overhead. MIG hardware isolation on RTX PRO 6000 Blackwell for memory-level GPU isolation.
  \item \textbf{Network Security:} Calico CNI with GlobalNetworkPolicy enforcing default-deny for all student namespaces; allow DNS resolution, outbound internet on ports 80/443, SSH gateway ingress; deny cross-namespace and control-plane access from student pods.
  \item \textbf{SSH Gateway:} Teleport bastion host for SSH access, with dynamic port-mapping per student pod and short-lived certificates.
  \item \textbf{Reaper Service:} Background task that checks for expired sessions every 10 seconds, triggers namespace deletion via K8s API, emits audit events via NATS JetStream, and sends notifications.
  \item \textbf{Audit Logging:} Full audit trail in PostgreSQL of all authentication events, session lifecycle transitions, and credit transactions.
  \item \textbf{Admin Interface:} Basic administrator dashboard for credit management, user management, and cluster-level GPU utilization view.
  \item \textbf{Notification Service:} Email/webhook notifications for session expiration warnings and completion events.
  \item \textbf{(VMpire)} Student and administrator views for \textbf{request queues}, \textbf{lifecycle extensions}, and \textbf{global workload overview} (phased delivery per SDD).
  \item \textbf{(VMpire)} \textbf{Quota policy} definitions and enforcement hooks aligned with course/department structure (may reuse credit ledger and Kubernetes quotas).
\end{itemize}

\subsection{Out of Scope}

\begin{itemize}[leftmargin=1.5em]
  \item Physical hardware provisioning or configuration of bare-metal GPU nodes.
  \item JupyterHub or any browser-based IDE.
  \item Custom container image registry or CI/CD pipelines for student images.
  \item Real-money payment processing or integration with external billing systems.
  \item Mobile native application (iOS/Android) - the portal is web-only.
  \item Multi-cluster federation or multi-region deployment.
  \item Object storage (S3-compatible buckets) or persistent dataset hosting.
\end{itemize}

\subsection{Assumptions and Constraints}

\subsubsection*{Technical Constraints}
\begin{itemize}[leftmargin=1.5em]
  \item The Kubernetes cluster runs on kubeadm or RKE2 (full Kubernetes, not K3s) on bare-metal nodes with pre-configured NVIDIA drivers and the NVIDIA GPU Operator (v25.3.1+) installed.
  \item gVisor (runsc) is deployed on all GPU nodes as the container runtime for student pods.
  \item The cluster is air-gapped from the public internet except for explicitly allowed outbound traffic (dataset downloads via Calico GlobalNetworkPolicy on ports 80/443).
  \item PostgreSQL 16 with TimescaleDB extension serves as the single source of truth for all application state, credit ledger, session data, and GPU metrics (time-series).
  \item Teleport is deployed in cluster and configured with a valid wildcard certificate for the institution's domain.
  \item NATS JetStream is deployed as the event bus for decoupled event processing between services.
\end{itemize}

\subsubsection*{Organizational Constraints}
\begin{itemize}[leftmargin=1.5em]
  \item Credits are allocated by administrators or instructors - students cannot self-purchase credits in v1.
  \item All users must authenticate via institutional SSO through Keycloak with SAML/OIDC identity brokering (Shibboleth IdP integration).
  \item The system must comply with the institution's data privacy policy - no student workload data leaves the cluster.
\end{itemize}

\subsubsection*{Timeline Constraints}
\begin{itemize}[leftmargin=1.5em]
  \item MVP targeting core provisioning, SSH access, and credit deduction must be ready within the four phases we have planned. 
  \item Admin dashboard and advanced analytics are v2 features.
\end{itemize}

\subsubhead{UC-01: Student Requests a New GPU Session}

\begin{tabularx}{\textwidth}{@{}L{4cm}X@{}}
  
  \rowcolor{rowalt}  \textbf{Field} & \textbf{Description} \\
  \midrule
  \textbf{Actor}        & Student \\
  \rowcolor{rowalt}  \textbf{Preconditions} & Student is authenticated; student has a positive credit balance; at least one GPU of the requested type is available. \\
  \textbf{Trigger}      & Student clicks ``Launch Session'' on a selected GPU profile in the portal. \\
  \rowcolor{rowalt}  \multicolumn{2}{@{}p{\textwidth}@{}}{\textbf{Main Flow}} \\
  \rowcolor{rowalt}  \multicolumn{2}{@{}p{\textwidth}@{}}{
    \begin{enumerate}[leftmargin=2em, topsep=0pt]
      \item Student selects desired GPU profile (e.g., RTX 3090 24GB) and clicks ``Launch Session.''
      \item Frontend sends a \texttt{POST /pods} request to the FastAPI control plane with the selected profile ID.
      \item Session Orchestrator validates that the student has sufficient credits for at least the minimum session duration.
      \item Orchestrator calls the K8s API via client-go to create a new namespace (\texttt{hopper-pod-<id>}) and provisions the student pod with the gVisor runtime class, GPU resource request, PVC, and resource limits.
      \item NVIDIA GPU Operator schedules the pod to an appropriate worker node with the requested GPU.
      \item Orchestrator generates an ephemeral SSH key pair, injects the public key into the pod via a K8s secret, and registers the pod with the Teleport gateway.
      \item Teleport returns an SSH connection string (e.g., \texttt{tsh ssh student@session-uuid.hopper.local}).
      \item Orchestrator writes the session record to the \texttt{pod\_sessions} table and begins the credit deduction timer.
      \item Frontend polls the session status endpoint and displays the SSH connection string along with a live credit counter.
    \end{enumerate}
  } \\
  \textbf{Alternate Flow} & \textit{Insufficient credits:} At step 3, if the student's balance is below the minimum session cost, the request returns an HTTP 402 and the frontend shows an ``Insufficient credits'' message. \\
  \rowcolor{rowalt}  \textbf{Exception Flow} & \textit{No GPU available:} If no node has free capacity for the requested profile at step 5, the Orchestrator returns HTTP 503 ``No capacity available'' and no session record is created. \\
  \textbf{Postconditions} & Pod is running, credits are being deducted, student has a valid SSH connection, audit log entry is written. \\
  
\end{tabularx}

\subsubhead{UC-02: Reaper Service Terminates an Expired Session}

\begin{tabularx}{\textwidth}{@{}L{4cm}X@{}}
  
  \rowcolor{rowalt}  \textbf{Field} & \textbf{Description} \\
  \midrule
  \textbf{Actor}        & Reaper Service (Async Worker) \\
  \rowcolor{rowalt}  \textbf{Preconditions} & One or more active sessions exist in the \texttt{pod\_sessions} table where either the credit balance is $\leq 0$ or the session has exceeded its TTL. \\
  \textbf{Trigger}      & Reaper's polling loop fires (every 10 seconds). \\
  \rowcolor{rowalt}  \multicolumn{2}{@{}p{\textwidth}@{}}{\textbf{Main Flow}} \\
  \rowcolor{rowalt}  \multicolumn{2}{@{}p{\textwidth}@{}}{
    \begin{enumerate}[leftmargin=2em, topsep=0pt]
      \item Reaper queries \texttt{pod\_sessions} for sessions where balance = 0 or \texttt{expires\_at < NOW()}.
      \item For each expired session, Reaper issues \texttt{kubectl delete namespace hopper-pod-<id> --cascade=foreground}.
      \item K8s deletes the pod, PVC, SSH secret, and all other resources in the namespace.
      \item Teleport revokes the SSH certificate associated with the session.
      \item Reaper updates the session status to \texttt{TERMINATED} in the \texttt{pod\_sessions} table.
      \item Reaper writes an audit log entry with the termination reason (credit exhaustion or TTL expiry).
      \item Notification Service sends the student a ``Session Ended'' email with session summary.
    \end{enumerate}
  } \\
  \textbf{Exception Flow} & If the K8s namespace deletion hangs, Reaper retries with exponential backoff (max 3 retries). After 3 failures, it escalates an alert to the admin notification channel. \\
  \rowcolor{rowalt}  \textbf{Postconditions} & Namespace is deleted, GPU is released back to the pool, student's session shows as ``Terminated'' in history, audit log is updated. \\
  
\end{tabularx}

\subsection{Data Model}
The core data model is a relational schema hosted in PostgreSQL 16 with TimescaleDB.
The main relationships are as follows:

\begin{itemize}[leftmargin=1.5em]
  \item \texttt{users} (1) $\rightarrow$ (1) \texttt{accounts}: each user has
    exactly one credit account (type: asset). A system revenue account (type: liability) handles the other side of all transfers.
  \item \texttt{transfers} (1) $\rightarrow$ (2) \texttt{ledger\_entries}: every
    transfer creates exactly two ledger entries (one debit, one credit) that sum to zero --- this is the core double-entry bookkeeping invariant.
  \item \texttt{accounts} (1) $\rightarrow$ (N) \texttt{ledger\_entries}: an account
    accumulates many ledger entries over time. The balance is derived from the most recent entry's \texttt{current\_balance} field.
  \item \texttt{users} (1) $\rightarrow$ (N) \texttt{pod\_sessions}: a user
    can have many sessions over time, with a configurable concurrent session limit (max 3 per source docs).
  \item \texttt{pod\_sessions} generate billing events that create transfers and corresponding ledger entries as the billing ticker fires on its per-minute interval.
  \item \texttt{gpu\_metrics} is a TimescaleDB hypertable storing time-series GPU telemetry with 1-hour chunks, compression, and continuous aggregates.
  \item \texttt{audit\_logs} holds a direct foreign key \texttt{actor\_id}
    $\rightarrow$ \texttt{users.id} to record \emph{who} performed an action.
    The \emph{target} of the action (a session or a transfer) is captured
    via the polymorphic pair \texttt{target\_type} / \texttt{target\_id} ---
    soft references used to keep the log append-only without hard FK
    constraints that would block cascading deletes on other tables.
\end{itemize}

Entity relationships are described in the preceding narrative; this revision does not include a graphical ER diagram (earlier mockup figures omitted).

\section{UI and UX Requirements}

\subsection{Wireframes}

The following six screens represent the primary user flows for the Hopper Cloud student portal. Illustrative mockup images are omitted; layouts are specified in prose below.

\subsubsection*{Screen 1 - Login Page}
A minimal, clean login screen with the Hopper Cloud logo, a ``Sign in with University SSO'' button (Keycloak OIDC), and a small note about what the platform is. No password field is shown - clicking the button redirects to the Keycloak authentication flow which brokers to the university's Shibboleth IdP. Error states for failed login attempts are displayed inline beneath the button.

\subsubsection*{Screen 2 - Student Dashboard (Home)}
The main landing page after login. Shows:
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=2pt]
  \item A prominent credit balance card with a real-time counter (live SSE streaming update).
  \item A summary card of the currently active session (if any) - showing GPU type, elapsed time, credits consumed, and a ``Stop Session'' button.
  \item A quick-launch panel showing available GPU profiles with their credit rate and availability badge (green/yellow/red).
  \item A recent session history table (last 5 sessions) with links to full history.
\end{itemize}

\subsubsection*{Screen 3 - Launch Session Modal/Page}
Triggered when a student clicks ``Launch'' on a GPU profile. Shows:
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=2pt]
  \item GPU profile details (GPU name, VRAM, credit rate, max duration).
  \item An estimated time calculator: input field for ``How many credits to use?'' with a calculated runtime.
  \item A ``Confirm Launch'' button and a loading spinner during provisioning.
  \item Once ready: a copyable SSH command string and a session timer.
\end{itemize}

\subsubsection*{Screen 4 - Active Session View}
A dedicated view for an in-progress session showing:
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=2pt]
  \item Large real-time credit counter (countdown style).
  \item Session details: GPU type, namespace, elapsed time, expiry time.
  \item SSH connection instructions and the connection string.
  \item A ``Stop Session'' button with a confirmation dialog.
  \item A credit warning banner that appears when projected time remaining drops below 10 minutes.
\end{itemize}

\subsubsection*{Screen 5 - Session History Page}
A full paginated table of all past sessions for the authenticated student. Columns include: Session ID (truncated), GPU type, Start time, End time, Duration, Credits consumed, Termination reason (manual, expired, credit exhaustion). Filterable by date range and GPU type.

\subsubsection*{Screen 6 (Admin) - Admin Dashboard}
Accessible only to admin-role users. Shows:
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=2pt]
  \item Cluster-level GPU utilization per node (heatmap or bar chart).
  \item A live table of all active sessions across all users.
  \item A user management panel with a credit allocation form.
  \item An audit log view with filtering.
\end{itemize}

\subsection{UX and Accessibility Baseline}

\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Navigation:} All primary actions reachable within 2 clicks from the dashboard. Breadcrumb navigation for admin views.
  \item \textbf{Labels:} All form fields and interactive elements have descriptive labels. No icon-only buttons without accessible tooltips.
  \item \textbf{Keyboard Accessibility:} Login, session launch, and session stop flows must be fully keyboard-navigable. Focus indicators must be visible.
  \item \textbf{Contrast:} All text/background combinations must meet WCAG 2.1 AA contrast ratio ($\geq 4.5:1$ for normal text).
  \item \textbf{Responsive Design:} Portal is usable at 1280px and wider (desktop-first). Tablet support (768px+) is a should-have.
  \item \textbf{Error States:} All API errors must surface a user-readable message - no raw error codes shown in the UI.
  \item \textbf{Loading States:} All async operations (session provisioning, credit updates) show a loading indicator so users aren't left wondering if something is happening.
\end{itemize}

\subsection{Open Questions}

\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Concurrent session limit per student:} Should students be allowed to run multiple concurrent sessions, or is there a hard cap of one active session per user? This needs a policy decision from admin stakeholders.
  \item \textbf{Credit refund policy:} If a session is terminated due to a system error (e.g., GPU node crash), will credits be refunded? If so, how is ``system fault'' distinguished from ``student-caused failure''? This needs a billing policy decision.
  \item \textbf{Container image selection:} In v1, will students be restricted to a set of approved base images (e.g., nvidia/cuda:12.x-devel), or will they be able to bring any Docker image? Allowing arbitrary images has significant security implications.
  \item \textbf{Persistent home directory:} Should there be an optional persistent volume that survives across sessions (for code, datasets) distinct from the per-session ephemeral PVC? This would be a significant UX improvement but adds storage management complexity.
  \item \textbf{Session sharing / collaboration:} Should two students ever be able to share a session for pair-programming or collaborative experiments? This is a v2 feature but the data model should not preclude it.
  \item \textbf{Time-zone handling:} Session expiry times should be displayed in the student's local time zone - how should the portal determine the user's time zone? Browser auto-detect vs.\ user profile setting?
  \item \textbf{Quota enforcement for instructors:} If an instructor allocates credits from a course budget, should the system enforce the total course budget as a hard cap, or just track it as a soft limit with admin alerts?
  \\
  \item \textbf{Support for Jupyter Notebooks in v2:} Should we design the API and the port-mapping layer to also support HTTP port forwarding (not just SSH) so that future versions can expose Jupyter or other web services? This may affect the Teleport configuration now.
\end{enumerate}
