\section{Problem Definition}

\subsection{Problem Statement}

\begin{itemize}
  \item \textbf{What problem are you solving?}\\
    Managing student virtual machines in academic environments is largely manual, error-prone, and resource-inefficient. Administrators spend significant time provisioning, tracking, and decommissioning VMs on request, with no standardized lifecycle enforcement. Students have no self-service visibility into their instances, leading to repeated requests, forgotten resources, and infrastructure sprawl.

  \item \textbf{Why does it matter?}\\
    Without a centralized provisioning system, labs face resource exhaustion, stale VMs consuming compute and storage, and no accountability for quota overuse. VMpire solves this by automating the full VM lifecycle --- from student request through admin approval to expiration --- while enforcing quotas and providing real-time visibility into instance ``vitals.'' This reduces admin overhead, prevents infrastructure abuse, and gives students a reliable, self-service experience.
\end{itemize}

\subsection{Goals and Non-Goals}

\textbf{Goals:}
\begin{itemize}
  \item Provide a self-service portal for students to request, view, and manage their VMs
  \item Enforce per-user and per-course resource quotas automatically
  \item Implement an approval workflow routing VM requests to the appropriate administrator
  \item Monitor and display real-time VM vitals (CPU, memory, storage, uptime, expiration status)
  \item Automate VM expiration and decommissioning based on configurable lifecycle policies
  \item Maintain a full audit trail of all provisioning and lifecycle events
\end{itemize}

\textbf{Non-goals:}
\begin{itemize}
  \item Building or managing the underlying hypervisor infrastructure (e.g., VMware, Proxmox, OpenStack)
  \item Providing a general-purpose cloud platform beyond student lab environments
  \item Supporting non-VM compute resources (e.g., bare metal, containers, Kubernetes)
  \item Replacing institutional identity management systems (SSO/LDAP are external)
  \item Billing or cost-chargeback functionality in v1
\end{itemize}

\section{Scope and Context}

\subsection{In Scope}

\begin{itemize}
  \item Student-facing self-service VM request form and dashboard
  \item Administrator approval and rejection workflow with notification support
  \item Quota definition, enforcement, and alerting (per user, per course)
  \item VM lifecycle management: provisioning, running, paused, expiring, expired, decommissioned states
  \item Real-time VM vitals monitoring dashboard (CPU, RAM, disk, network, expiration countdown)
  \item Automated expiration scheduling and decommissioning triggers
  \item Role-based access control (Student, Instructor, Lab Admin, System Admin)
  \item Audit log of all user and system actions
  \item Email/in-app notifications for request status changes, quota warnings, and expiration alerts
\end{itemize}

\subsection{Out of Scope}

\begin{itemize}
  \item Direct hypervisor management or configuration
  \item VM snapshot/backup management in v1
  \item Mobile native application (web-responsive only)
  \item Third-party marketplace or template store
  \item Billing, invoicing, or cost allocation
  \item Multi-institution or multi-tenant deployments in v1
\end{itemize}

\subsection{Assumptions and Constraints}

\textbf{Technical constraints:}
\begin{itemize}
  \item The platform must integrate with an existing hypervisor API (e.g., VMware vSphere, Proxmox, or OpenStack) via REST
  \item Institutional SSO (SAML/LDAP) is used for authentication; VMpire does not manage user credentials
  \item Initial deployment targets a single institution's network environment
\end{itemize}

\textbf{Organizational constraints:}
\begin{itemize}
  \item Lab administrators retain final approval authority over all VM provisioning requests
  \item Quota policies are defined by system administrators and may vary by course or department
\end{itemize}

\textbf{Timeline constraints:}
\begin{itemize}
  \item SRS v1 to be completed by end of Lab 2
  \item Prototype/MVP targeted for end of semester; full feature delivery phased
\end{itemize}

\subsection{Critical Use Cases}

\subsubsection*{UC-01: Student Submits VM Request}

\begin{itemize}
  \item \textbf{Preconditions:} Student is authenticated via SSO; student has not exceeded their resource quota
  \item \textbf{Main flow:}
    \begin{enumerate}
      \item Student navigates to ``Request VM'' page
      \item Student fills in OS template, vCPU count, RAM, disk size, and optional notes
      \item System validates inputs against quota limits
      \item Student submits the form
      \item System creates a request record in ``Pending'' state and routes it to the admin approval queue
      \item Student receives in-app and email confirmation
    \end{enumerate}
  \item \textbf{Alternate/exception flow:}
    \begin{itemize}
      \item If quota would be exceeded: system blocks submission and displays a quota-exceeded error
      \item If required fields are missing: form validation prevents submission with inline errors
    \end{itemize}
  \item \textbf{Postconditions:} A pending VM request exists in the admin queue; student dashboard shows ``Pending'' status
\end{itemize}

\subsubsection*{UC-02: Administrator Approves VM Request}

\begin{itemize}
  \item \textbf{Preconditions:} At least one pending request exists; administrator is authenticated
  \item \textbf{Main flow:}
    \begin{enumerate}
      \item Admin navigates to the approval queue
      \item Admin reviews request details (student, specs, course)
      \item Admin optionally sets expiration date, then clicks ``Approve''
      \item System calls the hypervisor API to provision the VM
      \item VM transitions to ``Provisioning,'' then ``Running'' upon successful hypervisor response
      \item Student is notified of approval and receives VM connection details
    \end{enumerate}
  \item \textbf{Alternate/exception flow:}
    \begin{itemize}
      \item If admin clicks ``Reject'': admin enters a reason; request is marked rejected; student notified
      \item If hypervisor API fails: VM stays in ``Provisioning'' state; admin is alerted; retry mechanism triggered
    \end{itemize}
  \item \textbf{Postconditions:} VM is running and visible on the student's dashboard with live vitals
\end{itemize}

\subsubsection*{UC-03: VM Expiration and Decommissioning}

\begin{itemize}
  \item \textbf{Preconditions:} A running VM has a configured expiration date/time
  \item \textbf{Main flow:}
    \begin{enumerate}
      \item System sends expiration warning notification to student 48 hours before expiry
      \item At expiration time, VM transitions to ``Expiring'' state
      \item If no extension request is approved within the grace period, VM transitions to ``Expired''
      \item After the grace period (24 hours), system calls the hypervisor API to decommission the VM
      \item VM transitions to ``Decommissioned''; resources are released; student is notified
      \item Audit log records all state transitions
    \end{enumerate}
  \item \textbf{Alternate/exception flow:}
    \begin{itemize}
      \item If student submits extension request before expiry: VM remains ``Running'' pending admin decision
      \item If decommissioning API call fails: system retries and alerts the system administrator
    \end{itemize}
  \item \textbf{Postconditions:} VM no longer exists in the hypervisor; resources freed; record retained in audit log
\end{itemize}

\begin{itemize}

    \end{itemize}
\end{itemize}

\subsection{UX and Accessibility Baseline}

\begin{itemize}
  \item Clear navigation hierarchy with role-appropriate menus (students see different nav than admins)
  \item All interactive elements are keyboard accessible; core flows completable without a mouse
  \item Colour contrast meets WCAG 2.1 AA minimum (4.5:1 for normal text)
  \item Status indicators use both colour and text/icon (not colour alone) for accessibility
  \item Responsive layout supports desktop and tablet viewports; mobile-readable at minimum
  \item Empty states and error messages provide actionable guidance (not just ``Error 400'')
  \item Expiration urgency communicated progressively (informational $\to$ warning $\to$ critical colour coding)
\end{itemize}

\subsection{Open Questions}

\begin{itemize}
  \item Which hypervisor platform(s) must be supported for the initial deployment --- VMware vSphere, Proxmox, OpenStack, or other?
  \item What is the institutional SSO provider --- Shibboleth, Azure AD, Okta? What attributes does it expose for role mapping?
  \item Should quota policies be configurable by instructors for their course, or exclusively by system admins?
  \item What is the defined grace period between VM expiration and automatic decommissioning?
  \item Are there regulatory or institutional data-retention requirements for audit logs beyond 1 year?
  \item Should the extension request flow require admin approval, or can it be auto-approved within certain bounds?
\end{itemize}
